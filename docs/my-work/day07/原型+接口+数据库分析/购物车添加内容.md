## 往购物车添加菜品/套餐

### 业务分析

1. 把菜品/套餐加入购物车
    * 菜品: 
        - 如果有口味(菜品规格), 点击设置后，再可点击加入购物车
        - 否则可以直接点击 `➕` 加购
    * 套餐: 直接点击 `➕` 加购

2. 点击购物车、进入
    * 加减菜品/套餐份数
    * 清空购物车

### 相关接口

1. 根据分类 id 展示菜品
    * GET + `/user/dish/list?categoryId=xxx`
    * List< DishVO >, DishVO = Dish + categoryName + DishFlavors

2. 根据分类 id 展示套餐
   * GET + `/user/setmeal/list?categoryId=xxx`
   * List< SetmealVO >, SetmealVO = Setmeal + categoryName 不包含 setmealDish 关联菜品

3. 查看菜品口味(规格)
    * 根据分类展示菜品时，DishVO 已经包含了菜品口味

4. 点击套餐查看套餐包含菜品
    * GET + `/user/setmeal/dish/{id}`
    * List< DishItemVO >, DishItemVO = setmealDish 中 dish 信息(copies,name) + Dish 部分信息(image)
    * 不过我更想叫 `SetmealDishVO` 明确表示套餐关联的菜品

5. 点击打开、展示购物车所有内容
    * GET + `/user/shoppingCart/list`
    * 不不不，其实套餐、菜品的内容对象已经在前端有了，这里直接用前端自己的数据展示就行
    * 而且菜品、套餐类型不统一，2 种 List 不好拿给前端
    * 但是如果要后端实现
      - 查出 List< SetmealVO >, List< DishVO >
      - 装成 List< Object > 返回前端
      - 前端根据接口文档转对象

6. 清除购物车
    * DELETE + `/user/shoppingCart`
    * 不过我感觉还是应该交给前端处理

7. 修改菜品/套餐份数
    * 也该前端

8. 提交购物车内容(结账)
    * POST + `/user/shoppingCart`
    * 需要传过来: 
      - 最少: 菜品 id 及其份数、套餐 id 及其份数
      - 当然传一堆 DishDTO、SetmealDTO 也行(但是这 2 个DTO是管理端用的，而且没 copies 属性)
    * RequestBody - ShoppingCartDTO = 
      - Map< DishShoppingDTO, Integer > + Map< SetmealShoppingDTO, Integer > 存放菜品信息、套餐信息、各自的份数
      - 上面这个需要拿到 Set< Entry > 遍历 key-value, 可能比较麻烦
      - List< DishShoppingDTO >, List< SetmealShoppingDTO >, 把菜品/套餐购物信息分别整合到一起


### 数据库表

1. setmeal
2. setmeal_dish
3. dish
4. shopping_cart

* 不过, 如果前端负责大部分数据处理，只在结账的时候提交菜品、套餐信息，那感觉购物车数据库表好像也没用
* 而且这么多菜品、套餐信息(就算只有 id、copies)，好像也没有数组来装(虽然可以拼成字符串)
* 可能只是相当于消费记录

```mysql
create table if not exists shopping_cart (
    id bigint primary key auto_increment comment '购物车数据库表 id',
    user_id bigint not null comment '该用户 id',
    create_time datetime not null default current_timestamp comment '结账时间',
    index idx_shopping_cart_user_id user_id
) comment '购物车表';
```

  三、你的分析中的问题 ❌

  1. 核心架构判断失误：购物车必须后端持久化

  你的观点："前端负责大部分数据处理...购物车数据库表好像也没用"

  这是最关键的错误。原因：

  - 多端同步：用户可能在小程序和 H5 之间切换，购物车数据需要跨端同步
  - 数据可靠性：前端存储（如 localStorage）不可靠，用户清缓存就丢失
  - 后续下单依赖：购物车数据直接用于生成订单，必须持久化
  - 用户登录状态：未登录时加购，登录后需要合并购物车数据

  2. 数据库表设计严重不足

  你的表设计：
  create table shopping_cart (
      id bigint primary key auto_increment,
      user_id bigint not null,
      create_time datetime not null default current_timestamp
  );

  缺失的关键字段：
  - name / image / amount：购物车展示需要商品信息，避免每次查询都 JOIN
  - dish_id / setmeal_id：区分菜品和套餐
  - dish_flavor：同一菜品不同口味是不同购物车项
  - number：记录数量

  ▎ 这些"冗余字段"（name, image, amount）是有意的设计，目的是减少查询时的表关联，提升购物车加载速度。

  3. 对"加减份数"的理解偏差

  你说"加减份数也该前端"，但教程的实现是：
  - 加：再次调用 add 接口，后端检测到同一商品已存在，则 number + 1
  - 减：教程 day07 中确实没有实现"减"的接口（这是一个小遗漏，实际应该提供）

  4. DTO 设计过度复杂

  你设计的提交结构：

  }

  原因：购物车是"逐条添加"的，不是"批量提交"的。用户每次点击 ➕ 只添加一个商品，不需要复杂的批量 DTO。
