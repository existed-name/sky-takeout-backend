# 我和教程的实现对比

---

* 顺序大致是 controller → service → mapper 由上到下
* 不过... 跟一个教学项目叫什么劲儿呢（（

<details>
<summary><h3>1. 请求格式设计</h3></summary>

* 教程是 RPC 风格（以动作为主），可以看到请求路径有动词
    - `/order/getInfo/{id}`
    - `/order/submit + dto`
    - `/employee/update + 包含 id 的 dto`
* 我改成了 RESTful 风格（以资源为主），请求方法表示动作，请求路径使用名词
    - ` GET /orders/{id}`
    - `POST /orders + dto`
    - `PUT /employees/{id} + 不包含 id 的 dto`( id 定位资源、PUT 表示修改、dto 只放该资源的信息 )
* 不过因为并没有改变协议，都用的 HTTP + json 传递数据，所以并没有性能区别
* 还是需要根据实际项目要求为准、统一风格

</details>


<details>
<summary><h3>2. 参数检验注解</h3></summary>

* controller 补上 `@Validated` 让该接口类能被检查, 接口方法的字段补上 `@Positive( message = "..." )` 等等约束
* 接口方法的 dto 参数补上 `@Valid`, dto 内部字段补上 `@NotNull/NotBlank/Positive/NotEmpty` 等等约束
* 更进一步使用分组检验，可以区分不同操作时需要检验的字段
    - 比如定义 `ValidationGroup` 接口, 再定义 Create、Update 内部接口
    - 于是 dto 的字段使用检验注解时，可以指定检验组 `@NotNull( message = "..", groups = { ValidationGroups.Update.class } )`
    - 然后 controller 方法给 dto 参数加上 `@Validated( value = ValidationGroups.Create.class )`
    - 这样就可以区分创建、更新时的字段场景, 只在创建/更新时才检验某个字段
* 另外, `@Positive/Min/Max/..` 等等注解只在字段非 null 时生效

</details>


<details>
<summary><h3>3. PageResult 补充泛型</h3></summary>

* 教程漏写了泛型，直接返回 PageResult, 这样有个现象是 knife4j 接口文档对于条件分页查询看不到包装的对象是什么
* 所以改成了 `PageResult< T >`

</details>


<details>
<summary><h3>4. 和前端交互的对象（dto/vo/Result/PageResult) 补充 Swagger 注解，完善接口文档</h3></summary>

* 顺带说一句，教程给 dto/vo 用的 `@ApiModel + @ApiModelProperty` 是旧版的 Swagger2( OpenApi2.0 )
* 可以换成新版 OpenAPI3 的 `@Schema` 注解


</details>


<details>
<summary><h3>5. 显式注入参数</h3></summary>

* service、mapper 依赖的变量尽量提取到方法参数列表，命名时 `[动作]By/With[条件,参数]`，明确依赖这个参数
* 比如获取当前管理员/用户 id 时, 交给 controller 获取，显式传入 service，这样单元测试方便 Mock，也方便接入其他接口（比如专门的测试接口，把用户/管理员id作为请求参数传入）

</details>


<details>
<summary><h3>6. 异常检验处理</h3></summary>

* 可能我的防御性过强了一点, 不知道有没有必要（但是心理上确实安全了）...
* controller 的检验注解负责基础格式检验，service 负责业务检验，拦截无效（没在白名单）的参数，以及订单状态是否支持特定操作...
* 印象比较深的是用户权限检验，用户之间的订单、购物车数据是隔离的，俩人之间不能互相访问数据，需要检验权限
* 于是我总结了几种实现方案
    - 核心是 mapper 操作带上用户 id, 避免只带订单 id, 在数据层做好防护
    - 简单的前置判断用 `countByOrderIdAndUserId`
    - 查询展示数据用 `selectByOrderIdAndUserId`
    - 更新数据用 `updateByOrderIdAndUserId`
    - 这样避免查询/修改其他用户的数据，同时统计行数/修改行数为 0、查询数据为 null 说明订单不存在或者不匹配当前用户
* 对于可以预料的、用户交互时的异常，抛出业务异常；程序员自己的问题、系统自己的问题/底层工具方法，日志记录当时的情况 + 抛出 JDK 原生异常；业务不能被阻断、就捕获异常输出日志；
* 比如我这里做了
    1. 主键回填判空, 主要用在需要设置逻辑外键的场景, 插入了主体数据、拿到它的 id 然后检验; 虽然说通常没问题、可能只在配置错的时候才会回填 null
    2. 用户再来一单, 需要把旧订单的数据复制到购物车，我检验、确保订单明细关联了套餐或者菜品（也就是逻辑外键是否存在），然后判断是否有已经停售/下架删除的套餐、菜品
    3. 封装 HttpClient 请求操作时
        * 每一步（构建 URI → 向 URI 发出请求 → 拿到响应体检查响应内容和状态 → 序列化为响应 json 字符串）捕获编译时异常/受检异常、日志记录当时的操作行为和参数和可能异常原因、包装为 IllegalState 或 UncheckedIOException 继续上抛
        * 便于出问题时排查是 URI 构建失败、响应状态码无效、json 序列化失败...
        * 有个细节, 直接在最外面套 try-catch 可能捕获内部某些代码的编译时异常，导致 1 处 catch 对应了多个异常点，所以我会先把最外面的 catch 块注释掉、从里到外 catch，这样好处是可以精确定位异常，缺点是 catch 块非常多（不过性能应该影响不大，报错概率很小）
    4. 最终全局异常处理器捕获所有业务异常、系统异常（进行了分类）返回友好信息给前端

</details>


<details>
<summary><h3>7. 常量枚举封装</h3></summary>

* 最开始我全部用的常量类，并且命名/负责模块也很宽，但是还好用、放些字段和简单方法
* 后来功能增加，我给一个模块/功能的常量类增加了几个静态内部类，分别负责同一功能不同方向的常量、方法，这个时候开始膨胀了
* 到后来，我发现职责明显太大、多个内部类混在一个常量类里面、还混杂了字段和方法，要调的话不舒服
* 于是把部分类拆开、重构成枚举，字段、方法（包括业务方法）放进去，这样做有效字段检查、常量/方法调用都比较方便、清晰
* 不过还是有一部分常量类没有拆，只能当作教训，以后尽可能每个小场景单独 1 个类，并且优先考虑枚举，纯字段（异常信息）、几乎不带业务方法才考虑常量类

</details>


<details>
<summary><h3>8. MapStruct 映射转换</h3></summary>

* 创建/修改场景，使用 converter 将 dto 映射为实体对象，避免了 BeanUtils.copyProperties 的反射性能问题
* 查询场景，对于字段非常多的 vo（比如订单相关的展示对象）考虑查询完整实体，然后使用 converter 筛掉部分字段、保留需要的字段
* 复制场景，比如用户再来一单需要把旧的订单明细的部分字段复制给新的购物车数据对象，于是 converter 接口参数使用 `@MappingTarget` 注解指定映射目标，把字段映射过去
* 创建了全局映射配置，同一设置各个 converter 的配置规则，指定在目标对象字段没有完全填充时报错，确保映射到位
* MapStruct 的使用
    - 可见 server 模块的 [converter](/sky-server/src/main/java/com/sky/converter) 接口代码,笔记写到了注释里面
    - MapStruct 接口编译后在 `sky-server/target/generated-sources/annotations/com/sky/converter` 里面生成实现类
    - 可以看到全是 getter, setter( 如果有 `@Builder` 那他会用 builder ), 性能自然比反射好
    - 可以链表转链表，但不能链表复制到另一个链表，因为不知道复制的顺序
    - 并且链表转链表，本质是循环调用单个对象转单个对象（所以还需要手动补上单个对象的映射）

</details>


<details>
<summary><h3>9. 对象解耦</h3></summary>

* 我的设计思路是: 划分多个对象, 每个对象都有自己的存在意义, 服务于特定场景、解除多场景复用同一个对象的耦合
1. 每个端点（功能点）都有自己的 vo, dto
    * 好处很明显, 隔离了各个业务场景, 他加减了字段不会影响我的数据处理/展示, 我要改字段不会担心影响别人
    * 约束: vo/dto 必须详细命名, `[业务角色端][资源模块][作用]`, 比如 `UserOrderHistoryItemVO` 表示用户端订单历史数据项( item 表示列表的 1 个元素 )
    * 这样用来区分场景（包括业务端）
    * 缺点是字有点长、vo/dto 数量很多（所以可以看到我项目里面给它们按照业务端、资源模块分了包）

</details>

<summary><h3>11. sql优化</h3></summary>

1. 批量更新
    * 比如停售菜品需要同步停售关联的套餐
    * 教程循环更新，一方面好想，一方面可以用到 `@AutoFill` 注解自动填单个对象的审计字段
    * 我这里用的一条 SQL 来更新，代价是需要 service 批量设置审计字段
    * 写法原理是 CASE-WHEN, 不同的 id 设置对应的值

        ```sql
        UPDATE setmeal
        SET status = CASE id
        WHEN 1 THEN #{某个status}
        WHEN 2 THEN #{某个status}
        WHEN 3 ...
        # 最后 WHERE id IN( ... )
          
        # 于是抽出
        UPDATE setmeal
        SET status = CASE id
        <foreach collection="setmealList" item="setmeal">
            WHEN #{setmeal.id} THEN #{setmeal.status}
        </foreach>
        # ...
        ```

    * 当然这里因为修改后的 status 都是一样的值，也可以直接全部 `SET status = #{status}`
    * 我这里为了突出批量更新、通用性, 就给每个 id 专门设置对应的字段
    * 另外定时任务也涉及批量更新订单状态
2. 只查询必要的字段，尽可能避免查询完整实体
    * 单个字段肯定直接查询了
    * 判断存在性用 `countBy条件`
    * 查询部分字段使用投影对象
        * 问题的背景:
            - 查全部字段/完整实体类会浪费很多字段，而我只会用到 2 ~ 3 个字段
            - 如果我创建 dto, 可能跟前端入参 dto 混在一起不好区分
            - 我又不可能每个字段单独查询
        * 所以查资料后选择 Projection 对象封装需要查询的字段
        * 并且命名时带上 `[资源模块][场景]` 同时注释使用场景
3. 联表查询的一点改进
    * 左右联表前分别查出需要的字段，再联表，减少笛卡尔积
    * 联表前先 WHERE 过滤，再进行联表
    * 不过好像 mysql 的优化器会自动帮我优化常规的 SQL，我这样改动后反而可能不能自动优化了
4. 提取公共 SQL 片段
    * 将数据库表完善字段、常用 vo 字段提取为 `BaseColumns` 等 SQL 片段, 查询时直接引用 `<include refid="XxxColumns"/>`
      - 看过大佬源码还提取过查询条件、筛选条件等等，应该写多了 SQL 就会提取了吧
    * 解决 `WHERE id IN( .. )` 空括号问题
      - 问题背景: 用户再来一单，如果上一单只点了套餐或者菜品时，数据库报错
      - 问题原因: 再来一单需要复制旧订单关联的套餐、菜品，并判断是否有停售/删除的数据，于是涉及 `WHERE id IN` 筛选，而用户只点了套餐或者菜品，那么必定出现空的 id 链表，导致传入 mapper 后报错
      - service 层解决方法: 涉及传入链表的操作需要先判空，空则跳过
      - mapper 层解决方法: 
        1. 进行兜底的链表判空检验, 空则直接 false, 否则再拼接 id 筛选条件
        2. 提取为公用 SQL 片段 `safeWhereIdIn`，对于参数为 `ids` 的 mapper 可直接复用、在 `WHERR` 后引用该片段
        3. 进一步提取参数名，支持调用方传入字段名、集合名, 对于参数为 `xxxIds` 的 mapper、甚至想筛选其他字段也能复用
        4. 具体可见[CommonSql.xml](/sky-server/src/main/resources/com/sky/mapper/common/CommonSql.xml)
5. 另外提一下，教程为了前端方便，对于统计数据封装为日期列表 + 数据列表, 我这里把日期、对应的数据封装到一起，变成一个 Count 对象，然后组装列表，这样方便后端维护
6. 其他的 SQL 忘了...

</details>

<summary><h3>12. redis 操作</h3></summary>

1. 指定缓存有效时间 ttl, 避免长时间不刷新、展示旧数据
2. 店铺状态因为改动频率很低，并且类似系统配置，所以不设置 ttl、永久保存、交给管理端修改
    * 使用 `@PostConstruct` 注解，在启动应用时初始化店铺状态
    * 不过这里因为管理端、用户端调用的同一个 service 查询方法，并且店铺状态不是真正的配置，也不需要专门初始化，所以直接在 service 查询方法里面 `setIfAbsent` 就行
3. 缓存今日订单数，用于组装订单号
    * 自定义订单号规则 `{业务码}{今天日期}{这是第多少个订单}`, 比如 `CQ202606201234567`( 支持 1 天近千万订单 )
    * 订单数量的记录，使用 redis 自增，保证一次下单对应一个订单号、并发时不会重叠计数
    * 教程的订单号用的当前时间戳（毫秒级），但在并发时可能会重叠
4. 精细控制缓存
    * 教程和我这里都用的 `分类 id → 菜品/套餐数据列表`，但我额外补了一个 `套餐 id → 这个套餐关联的菜品信息`
    * 我的思路是
      - 菜品完整数据 = 菜品本体数据 + 菜品口味，由于并没有单独的口味查询接口、并且口味的数据量不大，所以直接把口味和菜品信息放到一起，存完整的菜品 vo 列表
      - 套餐完整数据 = 套餐本体 + 关联菜品信息，关联菜品信息比较多、并且设置了单独的查询接口，于是套餐、关联菜品分开存放，需要的时候拿着套餐 id 查关联菜品
    * 具体表现在管理端修改了商品信息时，教程清除所有缓存，而我这里只清除受影响的那部分缓存
      - 修改菜品 → 这个菜品所在的列表受到影响 → 也就把该分类的数据清除就行
      - 修改套餐 → 再额外把套餐的关联菜品信息清除
      - 于是就无需清理所有分类缓存，用户端查询没被改动的分类依然可以复用缓存，直到下一次修改/过期
    * 我这里 RedisKey 用的冒号分隔，格式更规范
      - 教程的格式不太规范, 用下划线来分隔
      - 用冒号分隔时，RedisInsight 桌面端会自动把冒号前面的东西解析为文件夹，这样可视化看缓存的时候会有层级感
      - 另外也专门提取了 RedisKey 业务前缀常量
5. 教程用了 SpringCache 注解, 我觉得注解不够灵活、不如手写 redisTemplate 清晰, 并且为了统一风格，就都用的 redisTemplate
6. 管理端修改菜品、套餐涉及缓存删除, 于是我给他们提取出了[业务工具类](/sky-server/src/main/java/com/sky/utils)，共用组装 key、删除 key 的逻辑
    * 不过我现在看，确实有必要提取公共逻辑，但是只需要放到 service 内部变成私有方法就行，我这里抽象/封装程度太多

</details>

<summary><h3>14. 其他的</h3></summary>

1. 微信登录额外检查微信 API 错误响应码和响应信息
    * 看微信登录文档，如果返回了 errCode, errMsg, 说明登录出错
2. 事务注解
    * 教程只有一个 `@Transcational`
    * 我这里区分了使用场景
      - 只要涉及数据库修改, 就设置任何异常都事务回滚, `@Transcational( rollbackFor = Exception.class )`
      - 数据库只读场景，`@Transcational( readOnly = true )` 让框架优化查询性能
      - 不涉及数据库操作的服务方法，无需加事务注解, 避免多余的性能开销
3. 记录管理端操作日志
    * 自定义 `@LogOperaton` 注解，标记在管理端的写操作接口上，指定操作描述、操作类型
    * 再使用 AOP 切面方法将注解包含的字段、全限定方法名(`类全名(包路径.类名).方法名`)、请求参数json、异常信息持久化到数据库，用于跟踪排查
    * 不过有一点是，我这里没有写专门的日志展示查询接口，要看的话还是需要查库
    * 那么其实应该区分管理端 Admin 给开发、运维看，商家端 Business 才给商家看, 这里项目简单处理为商家端 = 管理端
